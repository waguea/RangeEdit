# Benchmark methodology

The goal is defensible measurements, not impressive-looking numbers. Every reported result
must include the corpus, hardware, compiler, flags, and run count.

## Corpora

Generated by scripts, never committed at large sizes:

| Corpus | Purpose |
|---|---|
| Random ASCII | Low match density, no linguistic structure |
| English prose | Realistic character distribution |
| Repetitive text | Adversarial for naive scanning |
| Log-like lines | Long lines, frequent delimiters |
| Pathological patterns | Worst cases for each algorithm |

Sizes: 1 MiB, 16 MiB, 100 MiB, 1 GiB (file I/O only where noted).

## Metrics

- Wall-clock time and throughput (MiB/s)
- Peak resident set size
- Allocation count and bytes allocated
- Time to first result
- Extension host responsiveness during a scan
- Cancellation latency

## Tools

- Google Benchmark for C++ microbenchmarks
- `hyperfine` for CLI end-to-end runs
- Node `perf_hooks` / `tinybench` for TypeScript baselines
- Instruments (macOS) or `heaptrack` / massif (Linux) for memory profiles

## Running

```sh
cmake --preset release
cmake --build --preset release
./build/release/engine/rangeedit_bench
```

Filter a single algorithm:

```sh
./build/release/engine/rangeedit_bench --benchmark_filter=BM_FindBmh
```

## Reporting rules

- Warm up, then report the median of at least 5 runs.
- State the exact hardware and OS.
- Record compiler version and optimization flags.
- Distinguish CPU time from wall time.
- Do not compare across different corpus sizes without normalizing.
- Report negative results. If TypeScript is close enough, say so.

## Decision gate (M4)

After the CLI and TypeScript baseline exist, compare:

1. Literal scan throughput on 1 MiB / 16 MiB / 100 MiB
2. Peak memory for 1 GiB streaming scans
3. Time to first result and cancellation latency
4. Build and distribution complexity

If C++ does not produce a meaningful advantage on the workloads RangeEdit targets, document
that in `docs/DECISIONS.md` and keep the simpler implementation as the default path.

## Results

### M4 decision gate (2026-11-05)

Environment:

- Apple M4 (10 cores), macOS 27.0
- Apple Clang 21.0.0, CMake Release (`-O3 -DNDEBUG`)
- Node.js v24.21.0
- Corpus: deterministic random lowercase ASCII with `needle` inserted every 4096 bytes starting
  at offset 1000; pattern `needle`
- C++ numbers come from `rangeedit_bench` (`BM_FindBmh`) and the release CLI.
- Node numbers come from `scripts/ts-baseline.ts`. Whole-file timing is scan-only; end-to-end
  rows include process startup and file reading.
- Timings are medians of 5 runs. Peak RSS was measured once per workload with
  `/usr/bin/time -l`.

Literal scan throughput:

| Corpus | C++ BMH | Node 24 `String.indexOf` | Node/C++ |
|---|---:|---:|---:|
| 1 MiB | 829.9 MiB/s | 934.3 MiB/s | 1.13x |
| 16 MiB | 782.3 MiB/s | 908.2 MiB/s | 1.16x |
| 100 MiB | 782.8 MiB/s | 906.1 MiB/s | 1.16x |

End-to-end and memory:

| Workload | C++ CLI | Node baseline |
|---|---|---|
| 100 MiB literal scan | 119.6 ms, 5.73 MiB peak RSS | 192.0 ms, 285.2 MiB peak RSS (whole-file) |
| 1 GiB literal scan, absent pattern | 1,135.4 ms, 5.73 MiB peak RSS | 595.0 ms, 144.4 MiB peak RSS (streaming) |

Interpretation:

- C++ BMH does **not** beat Node's native `String.indexOf` on literal scan throughput; Node is
  about 13-16% faster in the engine-only comparison.
- The C++ streaming CLI has a large memory advantage: roughly 25x lower peak RSS than Node
  streaming at 1 GiB and 50x lower than Node whole-file at 100 MiB.
- C++ wins the 100 MiB end-to-end CLI comparison, but loses the 1 GiB streaming comparison on
  this machine.
- Regex, edit application, UTF-16 conversion, time to first result, and cancellation latency
  are not part of this table. The CLI has no cancellation surface yet, so cancellation latency
  was deferred to M5 and is measured in the M5 addon gate below.

Decision: see ADR-0007 in `docs/DECISIONS.md`. Do not claim a C++ literal-throughput
advantage. Keep C++ as the memory-bounded and non-literal engine path; keep the TypeScript
fallback for small literal scans until the addon has end-to-end measurements.

### M5 addon gate (2026-11-05)

Environment is the same as the M4 run. The 100 MiB corpus is read once into a JavaScript string;
timings are medians of 5 runs with one warmup. Addon scan is the full `scan(text, "needle")`
result including Node-API string copy and JS match-array materialization. Node is
`String.indexOf` counted in the same process. Cancellation was triggered from `onProgress` after
the first 1 MiB checkpoint; latency is measured from `token.cancel()` to promise settlement.

| Measurement | Node 24 | Addon |
|---|---:|---:|
| Full scan throughput | 906.9 MiB/s (110.3 ms) | 680.4 MiB/s (147.0 ms) |
| First match | 0.006 ms | 8.846 ms |
| Cancellation latency | n/a | 0.025 ms |
| Cancellation success | n/a | 5/5 at ~1,048,578 code units |

Interpretation:

- The addon is slower than `String.indexOf` for in-memory literal scanning; the gap includes the
  mandatory UTF-16 copy and result materialization that the count-only Node baseline does not do.
- First-match latency is dominated by copying the whole string into native memory. The addon does
  not improve literal time-to-first-result on large documents.
- Once scanning starts, cancellation is sub-millisecond at the 1 MiB checkpoint. The measured
  latency excludes the initial string copy, which is not cancellable.
- M5 therefore does not overturn ADR-0007's literal default. See ADR-0008 for the operation split
  and ADR-0009 for the addon build/execution model.

### M6 extension host (2026-11-05)

The M6 integration suite runs inside VS Code 1.145.0 and verifies the fallback literal path, the
forced addon literal path, addon-backed regex, replace/delete through `WorkspaceEdit`, and
selection scoping. This is a functional integration test, not a performance benchmark. No
extension-host throughput or time-to-first-result claim is made from it.

### Reproduction

M4:

```sh
node scripts/generate-corpus.ts --output /tmp/rangeedit-m4/random-100.bin --size-mib 100
node scripts/ts-baseline.ts --file /tmp/rangeedit-m4/random-100.bin --pattern needle --runs 5
./build/release/engine/rangeedit_bench --benchmark_filter=BM_FindBmh --benchmark_min_time=0.2s
```

M5:

```sh
cmake --preset addon
cmake --build --preset addon --parallel
node --experimental-strip-types scripts/addon-baseline.ts \
  --file /tmp/rangeedit-m4/random-100.bin --pattern needle --runs 5
```
